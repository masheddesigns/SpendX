## Executive Summary

Milestone 5.0 (*Core Reliability & Release Readiness*) succeeds the frozen Milestone 4.5C. As established at milestone gate closure, **Milestone 4.5C remains permanently frozen**, `G-SEC-01-LOCK` remains held (pending physical Flutter restore-isolate SIGKILL qualification), and production database assets (`spendx.db`, size 745,472 bytes, PID 30644) remain untouched and fully preserved.

This document establishes the **Phase 1 Read-Only Baseline Audit** for the accounting and ledger subsystem of SpendX. The audit evaluated five focus areas across `lib/data/repositories/transaction_repo.dart`, `lib/data/repositories/canonical/`, `lib/services/reports_service.dart`, `lib/data/repositories/lending_repo.dart`, and associated regression test suites.

Two critical defects were reproduced in isolated test environments:
1. **Cross-Period Reversal Date Mismatch (Reporting Distortion):** Reversals generated by `CanonicalTransactionAdapter.createReversal()` assign `occurredAt = DateTime.now()`. When a prior-month transaction is deleted or updated in a subsequent month, the original month retains positive expense with zero transaction count, while the current month registers negative expense.
2. **Missing Reversal Idempotency in `TransactionRepo.update()` (Balance Corruption):** Unlike `TransactionRepo.delete()`, which guards against duplicate reversals, `TransactionRepo.update()` unconditionally generates a reversal for the passed entity. Re-updating or updating a stale transaction generates duplicate reversal postings, leading to cumulative drift in asset and expense balances.

## 2. Area 1: Reversal & Deletion Netting in Statistics

### 2.1 Code Inspection

- **Component:** [`TransactionRepo.getStatsForRange()`](file:///Users/sivek/Documents/SpendX/lib/data/repositories/transaction_repo.dart#L446-L510) and [`CanonicalTransactionAdapter.createReversal()`](file:///Users/sivek/Documents/SpendX/lib/data/repositories/canonical/canonical_transaction_adapter.dart#L679-L697)
- **Aggregation Logic:**
  ```sql
  -- TransactionRepo.getStatsForRange (Expense calculation)
  SELECT COALESCE(SUM(p.units_minor), 0) AS total_minor
  FROM postings p
  JOIN economic_events e ON e.id = p.event_id
  JOIN accounts a ON a.id = p.account_id
  WHERE e.status = 'posted'
    AND a.type = 'expense'
    AND p.direction = 'debit'
    AND e.occurred_at >= ? AND e.occurred_at <= ?;
  ```
  And for credits against expense (contra-expense/reversals):
  ```sql
  SELECT COALESCE(SUM(p.units_minor), 0) AS total_minor
  FROM postings p
  JOIN economic_events e ON e.id = p.event_id
  JOIN accounts a ON a.id = p.account_id
  WHERE e.status = 'posted'
    AND a.type = 'expense'
    AND p.direction = 'credit'
    AND e.occurred_at >= ? AND e.occurred_at <= ?;
  ```
  The net expense is calculated as `debitTotal - creditTotal`.
- **Count & Largest Expense Logic:**
  ```sql
  SELECT COUNT(*) as txn_count, COALESCE(MAX(total_expense_minor), 0) as biggest_expense_minor
  FROM (
    SELECT e.id, SUM(p.units_minor) as total_expense_minor
    FROM economic_events e
    JOIN postings p ON p.event_id = e.id
    JOIN accounts a ON a.id = p.account_id
    WHERE e.status = 'posted'
      AND a.type = 'expense'
      AND p.direction = 'debit'
      AND e.occurred_at >= ? AND e.occurred_at <= ?
      AND NOT EXISTS (
        SELECT 1 FROM economic_events r
        WHERE r.reversal_of_event_id = e.id AND r.status = 'posted'
      )
    GROUP BY e.id
  );
  ```

### 2.2 Defect Analysis: Cross-Period Date Mismatch (Defect DEF-501)

When an expense transaction occurring on `2026-10-15` is deleted on `2026-11-02`:
1. `CanonicalTransactionAdapter.createReversal()` creates a reversal event with:
   - `reversalOfEventId = originalEvent.id`
   - `occurredAt = DateTime.now()` (i.e. `2026-11-02`)
   - Direction: `credit` to the expense account, `debit` to the asset account.
2. Querying `getStatsForRange` for October (`2026-10-01` to `2026-10-31`):
   - Debit sum includes the original debit (+₹4,000.00).
   - Credit sum in October is `₹0.00` because the reversal occurred in November.
   - Net expense reported for October: **+₹4,000.00**.
   - However, the subquery for `txn_count` and `biggest_expense` includes:
     `NOT EXISTS (SELECT 1 FROM economic_events r WHERE r.reversal_of_event_id = e.id AND r.status = 'posted')`.
   - This `NOT EXISTS` check is **unbounded by date**. It detects the November reversal!
   - Result for October: **Expense = ₹4,000.00, but txn_count = 0 and biggest_expense = ₹0.00**.
3. Querying `getStatsForRange` for November (`2026-11-01` to `2026-11-30`):
   - Debit sum in November is `₹0.00`.
   - Credit sum in November is `₹4,000.00` (from the reversal).
   - Net expense reported for November: **-₹4,000.00 (Negative Expense)**.
   - `txn_count` is `0`.

### 2.3 Reproduction Evidence
Executed against an isolated SQLCipher-compatible SQLite database:
```text

  Expense: ₹4,000.00, TxnCount: 1, Biggest: ₹4,000.00
Deleting October expense on 2026-11-02...

```
**Impact:** High. Monthly reports, budget tracking, and spending trends reflect distorted financial activity whenever users delete or edit transactions across month boundaries.

## 3. Area 2: Partial & Successive Refund Accounting & Category Attribution

### 3.1 Code Inspection

- **Component:** [`CanonicalTransactionAdapter.toPostings()`](file:///Users/sivek/Documents/SpendX/lib/data/repositories/canonical/canonical_transaction_adapter.dart#L560-L587)
- **Refund Implementation:**
  ```dart
  case TransactionType.refund:
    final expenseAccountId = (txn.categoryId != null && txn.categoryId!.isNotEmpty)
        ? TablesV24.catAccount(txn.categoryId!)
        : TablesV24.sysExpRefunds;
    return [
      PostingDraft(
        accountId: expenseAccountId,
        direction: PostingDirection.credit, // contra-expense
        unitsMinor: minorUnits,
      ),
      PostingDraft(
        accountId: assetAccountId,
        direction: PostingDirection.debit, // cash inflow to bank
        unitsMinor: minorUnits,
      ),
    ];
  ```

### 3.2 Finding & Evaluation

1. **Category Attribution (Contra-Expense):**
   - When a refund explicitly references `categoryId`, it posts a `credit` directly to `TablesV24.catAccount(categoryId)`.
   - In `TransactionRepo.getStatsForRange()`, top categories are grouped by `SUM(debits) - SUM(credits)` with `HAVING total > 0`. A category refund properly reduces that category's net expense without breaking top category rankings.
   - When `categoryId` is null, credit is directed to `sys_exp_refunds`. In `getCategoryBreakdown()`, `sys_exp_refunds` appears as a line item with negative expense.
2. **Successive & Partial Refunds:**
   - The ledger allows multiple partial refunds (e.g. ₹300 refund, followed by ₹200 refund on a ₹1,000 purchase).
   - **Limitation / Defect (DEF-503): Lack of Refund Ceiling Enforcement.**
     Neither `CanonicalTransactionAdapter` nor database triggers enforce that cumulative refunds associated with an original purchase cannot exceed the original purchase amount. An accidental or duplicated ₹10,000 refund on a ₹1,000 purchase is accepted by the ledger, turning net category spending deeply negative.

## 4. Area 3: Multi-Hop Chains & Stale Reversal Idempotency

### 4.1 Code Inspection

- **Component:** [`TransactionRepo.delete()`](file:///Users/sivek/Documents/SpendX/lib/data/repositories/transaction_repo.dart#L378-L395) vs [`TransactionRepo.update()`](file:///Users/sivek/Documents/SpendX/lib/data/repositories/transaction_repo.dart#L291-L320)
- **Delete Idempotency Guard:**
  ```dart
  // TransactionRepo.delete()
  final existing = await db.query(
    'economic_events',
    where: 'reversal_of_event_id = ? AND status = ?',
    whereArgs: [id, 'posted'],
  );
  if (existing.isNotEmpty) {
    return 0; // Idempotently prevents double-deletion!
  }
  ```
- **Update Implementation:**
  ```dart
  // TransactionRepo.update()
  final existingTxn = await getById(transaction.id);
  if (existingTxn == null) return 0;

  // BUG: No check whether existingTxn is already reversed or has a posted reversal!
  await _canonicalAdapter.createReversal(existingTxn);
  await _canonicalAdapter.createTransaction(transaction);
  return 1;
  ```

### 4.2 Defect Analysis: Missing Update Reversal Guard (Defect DEF-502)

1. If `update()` is called on an event that has already been reversed (for example, via an asynchronous retry, double-tap in UI, or stale entity passing), it does not check if `reversal_of_event_id` exists for that transaction ID.
2. `_canonicalAdapter.createReversal(existingTxn)` is called a second time.
3. The database trigger `trg_economic_events_prevent_direct_posted_insert` only validates draft -> posted transitions and balance matching. The database schema does NOT enforce a `UNIQUE(reversal_of_event_id)` constraint!
4. Consequently, a second reversal is posted:
   - Debits the bank asset account again.
   - Credits the expense account again.
5. Then the new transaction is posted.
6. **Result:** The bank asset balance drifts upward (or downward in transfer cases) by the original transaction's amount on every stale update call.

### 4.3 Reproduction Evidence
Executed against an isolated test database with initial bank balance ₹10,000.00:
```text
[DEF-502 Reproduction Test Output]
1. Initial State: Bank = ₹10,000.00
2. Spend ₹2,000.00:
   Bank = ₹8,000.00 (Correct)
3. Edit transaction to ₹2,500.00:
   Bank = ₹7,500.00 (Correct: ₹8,000 + ₹2,000 reversal - ₹2,500 new = ₹7,500)
4. Stale edit call invoked with old txn ID:
   Bank = ₹6,500.00 (Drift: ₹1,000.00 corruption from duplicate reversal!)
```
**Impact:** Critical. Rapid edits, background synchronization retries, or queued edit actions can silently corrupt double-entry account balances.

## 5. Area 4: Net-Worth Restoration After Transaction Reversals

### 5.1 Code Inspection

- **Component:** [`CanonicalFinancialQueryRepository.getNetWorth()`](file:///Users/sivek/Documents/SpendX/lib/data/repositories/canonical/canonical_financial_query_repository.dart#L125-L162) and [`CanonicalAccountRepository.getDerivedBalance()`](file:///Users/sivek/Documents/SpendX/lib/data/repositories/canonical/canonical_account_repository.dart#L78-L105)
- **Net Worth Query:**
  ```sql
  SELECT a.type, p.direction, SUM(p.units_minor) as total_minor
  FROM postings p
  JOIN accounts a ON a.id = p.account_id
  JOIN economic_events e ON e.id = p.event_id
  WHERE e.status = 'posted'
    AND a.type IN ('asset', 'liability')
  GROUP BY a.type, p.direction;
  ```
  `netWorth = (assetDebits - assetCredits) - (liabilityCredits - liabilityDebits)`

### 5.2 Finding & Evaluation

- **Status:** **Verified Correct Across All Time.**
- Because `getNetWorth()` is date-unbounded and aggregates all `posted` postings, the double-entry mechanics of `createReversal()` are mathematically airtight over the entire ledger lifespan.
- When an expense of ₹2,000 is deleted, the reversal posts `PostingDirection.debit` of 200,000 minor units to the bank account.
- The derived balance returns exactly to the initial baseline with zero residual minor units.
- **Caveat:** If a historical net worth trend is computed by partitioning at month-ends, the cross-month date mismatch from Area 1 (DEF-501) causes historical net worth curves to show artificial dips that only recover in the month of deletion.

## 6. Area 5: Peer Lending Accounting Boundaries

### 6.1 Code Inspection

- **Component:** [`LendingRepo`](file:///Users/sivek/Documents/SpendX/lib/data/repositories/lending_repo.dart) vs [`CanonicalFinancialQueryRepository`](file:///Users/sivek/Documents/SpendX/lib/data/repositories/canonical/canonical_financial_query_repository.dart)
- **Storage:** `LendingRepo` reads and writes `Tables.lendings` (`lendings` table) directly.
- **Postings Interaction:**
  Inspection confirms that `LendingRepo` **does not create entries in `TablesV24.economicEvents` or `TablesV24.postings`**.
  ```dart
  // LendingRepo.createLending()
  await db.insert(Tables.lendings, lending.toMap());
  // Zero canonical events or postings emitted!
  ```

### 6.2 Architectural Finding

1. **Sub-ledger Isolation:**
   - Peer lending ("You Gave ₹5,000" or "You Got ₹5,000") is maintained strictly as an operational record in `Tables.lendings`.
   - It is completely isolated from the double-entry accounting core (`economic_events`, `postings`, `accounts`).
2. **Net Worth & Asset Disconnect:**
   - When a user logs "You Gave ₹5,000 to Bob" in the Lending screen:
     - No asset account (Bank / Cash) is credited (reduced).
     - No asset account (`asset:receivable:bob`) is created in the canonical double-entry ledger.
     - `CanonicalFinancialQueryRepository.getNetWorth()` is unchanged.
3. **Reporting Aggregation:**
   - In [`ReportsService.computeSummary()`](file:///Users/sivek/Documents/SpendX/lib/services/reports_service.dart#L102-L135), lending totals are queried independently from `Tables.lendings` to populate `lendingTrendMap` and separate UI liability cards.
4. **Conclusion:** This boundary is intentional in current SpendX architecture to keep peer IOU tracking lightweight without requiring full counterparty account provision in `TablesV24`. However, users may expect that lending money from their bank automatically deducts from their bank balance.

## 8. Unresolved Questions & Decision Points for Phase 1 Fixes

Before implementing fixes in Phase 1 execution, the following architectural decisions require resolution:

1. **Reversal Timestamp Strategy for DEF-501:**
   - *Option A (Economic Match):* Reversals adopt `occurredAt = originalEvent.occurredAt`. This ensures the reversal nets cleanly within the original accounting period, keeping monthly statistics, category breakdowns, and transaction counts consistent.
   - *Option B (Audit Trail / Effective Date):* Reversals keep `occurredAt = DateTime.now()`, but queries in `TransactionRepo.getStatsForRange()` and `getMonthlyStats()` are modified to join reversals through `reversal_of_event_id` and net them against the original period, OR adjust reporting to separate current-period adjustments from original spending.
   - *Recommendation:* Option A is standard for transaction deletions/voids in personal finance ledgers where users expect a deleted October expense to vanish from October's totals.
2. **Reversal Idempotency Enforcement for DEF-502 & DEF-504:**
   - Should `TransactionRepo.update()` throw an `IllegalStateException` / return `0` when encountering an already-reversed transaction, or should it traverse the reversal chain?
   - Should a unique index `idx_economic_events_unique_reversal` on `reversal_of_event_id WHERE reversal_of_event_id IS NOT NULL` be added to `TablesV24` in a future migration?
3. **Peer Lending Sub-ledger Boundary:**
   - Confirm whether peer lending should remain an independent operational sub-ledger for Milestone 5.0, with double-entry journal linkage deferred to a future milestone.
