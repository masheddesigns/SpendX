**Target:** SpendX 2.1.0  
**Phase:** Pillar 4.5A.1.22 — Database Quiescence Proof and OS Lock Uncertainty  
**Status:** Complete — Architecture Closed with Explicit Implementation Gate

## 1. Executive Summary & Defect Statement

In SpendX 2.1.0, database-at-rest encryption was implemented using SQLCipher with a 256-bit AES master key generated by `SpendXDatabaseKeyManager` and stored locally in platform secure storage (`FlutterSecureStorage` via Android Keystore / iOS Keychain). 

However, the backup subsystem (`BackupService`) creates database snapshots using SQLite's native `VACUUM INTO`:
```dart
await db.execute("VACUUM INTO '${snapFile.path}';");
```
When `db` is an encrypted SQLCipher database, `VACUUM INTO` produces a replica database page snapshot that **remains encrypted with the local device's unique SQLCipher master key**. 

As a result:
- **Same-device restore (original key present):** Succeeds.
- **Cross-device restore (Device B):** Fails with SQLCipher error 26 / `SQLITE_NOTADB` because Device B possesses a different hardware-backed master key.
- **Reinstall / Data Wipe restore:** Fails because uninstalling or clearing app data wipes the master key from Keystore/Keychain, preventing the user from ever recovering their data.

This is a confirmed portability defect (SEC-01).

## 2. Rejection of Email-Derived Encryption Keys

### 2.1 Architectural Decision
A previous draft proposed deriving backup encryption keys from a Google account email for background sync. **This proposal is completely rejected.**

### 2.2 Security Principles
1. **Public Identifiers Are Not Cryptographic Secrets:** An email address, Google account ID, or device serial number is a public or semi-public identifier. Deriving cryptographic encryption keys from identifiers accessible to third parties, server logs, or platform APIs compromises cryptographic confidentiality.
2. **Strict Separation of Concerns:**
   - **Google Drive Authentication:** Controls only transport and remote storage authorization (OAuth 2.0 access token).
   - **Backup Encryption:** Bound exclusively to a high-entropy user-controlled password or recovery secret via Argon2id.
   - **Device Database Keys:** Generated by `SpendXDatabaseKeyManager` on the local hardware keystore and bound strictly to the local device boundary.
3. **Cross-Device Restore Requirement:** Cross-device restoration strictly requires the user to input the backup credential. No device or cloud service may bypass this credential.
4. **Unresolved Product Decision:** Automated, silent background cross-device sync (without user credential input) requires asymmetric key agreement or a cloud KMS vault. Until such an infrastructure is architected, SpendX will **not implement an implicit key-sharing mechanism**. Cloud sync will require the user to configure a backup password or recovery key.

## 4. Durability Realities & Synchronization Boundaries

SpendX replaces absolute claims regarding storage durability with precise, qualified engineering contracts:

### 4.1 Definition of Durability Confirmation
Durability confirmation is defined strictly as the **successful return of required file-level and directory-level synchronization system calls within the OS/filesystem contract**:
- It does **not** assert physical immunity against hardware flash controller failure, unexpected disk wear, battery-backed write-cache loss, or catastrophic physical destruction.
- It asserts that the application has completed all prescribed OS-level synchronization primitives (`fsync()` on file descriptors and `fsync(dir_fd)` on parent directory descriptors) and that zero I/O errors were reported by the kernel.

### 4.2 Synchronization Invariants & File Inventory
The following files and directories participate in the synchronization contract:
1. **Database Files Requiring File Sync (`fsync()`):**
   - Active database: `spendx.db`
   - Restored staging database: `spendx.db.restored`
   - Safety backup database: `spendx.db.pre_restore_backup`
   - Rollback staging copy: `spendx.db.rollback_staging`
   - Quarantined databases: `spendx.db.corrupt_<opId>_<timestamp>`
   - Restore journal: `spendx_restore_journal.json`
2. **Directories Requiring Directory Sync (`fsync(dir_fd)`):**
   - Application database parent directory (containing `spendx.db`, safety backups, staging files, and lockfile).
   - Journal parent directory (co-located in database directory).
3. **Strict Sequencing of Operations:**
   ```text
   File Flush/Sync -> Atomic Rename -> Directory Sync -> Journal Update/Sync -> Directory Sync -> Cleanup
   ```
4. **Behavior on Synchronization Failure or Unavailability:**
   - If any required file `fsync()` fails: halt immediately; do not proceed to rename.
   - If directory `fsync()` is unavailable (pure Dart `dart:io`): durability status is classified as **Durability Unconfirmed**; safety backup and journal remain **retained**.
   - If directory `fsync()` fails (`EIO`): halt immediately; do not delete any safety artifact; report storage error.

## 5. Non-Destructive Rollback Protocol & Preservation Terminology

### 5.1 Preservation Terminology Distinction
- SpendX replaces "100% intact" with **"unmodified and retained by the application."**
- Retention confirms that the application has not unlinked, overwritten, or modified the file.
- Retention is strictly separated from durability confirmation: retention does not imply power-loss survival unless all required sync operations succeeded.

### 5.2 Non-Destructive Rollback Protocol
To preserve the original safety backup until the restored active database is fully verified:
1. **Validate Safety Backup:** Open `spendx.db.pre_restore_backup` and verify 7-point deep integrity and fingerprint.
2. **Quarantine Invalid Active DB:** Rename corrupt active `spendx.db` $\rightarrow$ `spendx.db.corrupt_<opId>_<timestamp>` using no-replace. Confirm destination vacancy.
3. **Create Rollback Staging Copy:**
   - Copy `spendx.db.pre_restore_backup` to:
     ```text
     spendx.db.rollback_staging
     ```
   - Flush and sync the staging copy.
   - **Crucial Invariant:** `spendx.db.pre_restore_backup` **REMAINS UNMODIFIED AND RETAINED BY THE APPLICATION** on disk.
4. **Validate Rollback Staging Copy:** Validate `spendx.db.rollback_staging` against `expectedPreRestoreFingerprint`.
5. **Rename Staging to Active:** Rename `spendx.db.rollback_staging` $\rightarrow$ `spendx.db` using no-replace.
6. **Post-Rollback 7-Point Deep Validation:** Deep-validate `spendx.db`.
7. **Record Rollback in Journal:** Update journal to `state: rolledBack`.
8. **Retirement / Retention Rule:**
   - The safety backup `spendx.db.pre_restore_backup` is eligible for retirement **only** after Steps 1–7 have all succeeded AND native directory synchronization confirms durability.
   - Under pure Dart runtime (durability unconfirmed), `spendx.db.pre_restore_backup` is **retained indefinitely** alongside the journal.
   - If copy, quarantine, rename, or validation fails at any point: **HALT IMMEDIATELY**. The original safety backup `spendx.db.pre_restore_backup` remains unmodified and retained on disk.

## 6. Coordinator Ownership, Readiness Protocol & Removal of False CAS Claim

### 6.1 Corrected Ownership & Readiness Ordering
A candidate coordinator must **never publish its endpoint before acquiring the OS-level lock**. Publishing before lock acquisition creates an unsafe race window where callers discover an unready or non-owning coordinator.

The lifecycle is redesigned into six strict sequential phases:
```text
Phase 1 (Unpublished / Starting):
        - Candidate isolate spawns in an unpublished, unready state.
        - Does NOT register with IsolateNameServer.

Phase 2 (OS Lock Acquisition):
        - Candidate opens 'spendx_restore.lock'.
        - Issues exclusive file lock (RandomAccessFile.lock(FileLock.exclusive)).
        - If acquisition fails (e.g. held by another process/engine):
          Candidate self-terminates immediately. Port is NEVER published.

Phase 3 (Identity Generation):
        - Candidate generates unique 'coordinatorInstanceId' (UUIDv4 + timestamp).

Phase 4 (Endpoint Publication):
        - Holding the OS lock, candidate registers port with IsolateNameServer.
        - If an old mapping exists, candidate cleans it up under lock protection.

Phase 5 (Readiness Announcement):
        - Candidate transitions state to CoordinatorState.ready.
        - Begins listening for Handshake requests.

Phase 6 (Caller Handshake & Operation Submission):
        - Caller discovers port and sends HandshakeRequest(nonce).
        - Candidate replies with HandshakeResponse(nonce, coordinatorInstanceId, ready).
        - Caller submits database requests ONLY after receiving valid ready handshake.
```

### 6.2 Removal of False CAS Claim & Ownership Realities
- **Removal of False CAS Claim:** The sequence `lookupPortByName` + compare in Dart + `removePortNameMapping` in Flutter is **not atomic**. Describing it as a Compare-and-Swap was a defect.
- **Authoritative Resolution:**
  - Callers are **STRICTLY PROHIBITED** from calling `removePortNameMapping()`.
  - Stale port mappings are never removed by arbitrary callers based on timeouts.
  - Only a candidate isolate that has **already acquired the exclusive OS-level file lock** (`spendx_restore.lock`) is authorized to manage or overwrite the `IsolateNameServer` mapping.
  - Because the OS lock is exclusive across all processes and threads, concurrent mapping registration races are serialized at the OS filesystem boundary.

### 6.3 Strengthened Liveness, Correlation & Indeterminate State
- **Timeout != Termination:** A message timeout or slow response does **not** prove coordinator death. Coordinators may be busy with multi-gigabyte cryptographic streaming.
- **Instance ID & Request Correlation:** Every request carries a unique `requestId`; every response carries `(requestId, coordinatorInstanceId, status, payload)`.
- **Indeterminate State Policy:** If a caller experiences a timeout during an ongoing operation:
  - The caller transitions its local state to `CoordinatorState.indeterminate`.
  - The caller **must not** assume coordinator termination.
  - The caller **must not** attempt to spawn a replacement coordinator.
  - The caller aborts its own wait with `RestoreIndeterminateException` and leaves all database files untouched.
- **Recovery After Confirmed Termination:** Only when isolate termination is positively confirmed (exit listener fired, OS lock released, or process termination) may a new candidate attempt OS lock acquisition.

## 7. Flutter Engine & Process Boundary Realities

### 7.1 Coordination Boundaries
1. **Single Flutter Engine Isolates:**
   - Isolates spawned from the same root Flutter engine (e.g. via `compute()`, background worker isolates sharing the Dart VM isolate group) can communicate via `SendPort` and resolve mappings through `IsolateNameServer`.
2. **Separate Flutter Engines:**
   - Background execution callbacks executed via `@pragma('vm:entry-point')` (specifically `notificationTapBackground` in [`lib/services/notification_service_v2.dart`](file:///Users/sivek/Documents/SpendX/lib/services/notification_service_v2.dart#L1366)) run in an **independent background FlutterEngine** spawned by Android when the app is terminated.
   - Separate Flutter engines and independent OS processes do **not** share `IsolateNameServer` memory.
3. **Cross-Engine & Cross-Process Mutual Exclusion:**
   - Mutual exclusion across separate Flutter engines and separate OS processes relies exclusively on the **OS-level file lock** (`spendx_restore.lock`).
   - Every independent engine or process that executes restore/recovery must acquire the OS lock itself. It must never assume the UI engine's coordinator or `IsolateNameServer` mapping is shared.
4. **Strict Prohibition Against Coordinator Bypass:**
   - An isolate or background task unable to reach the coordinator must **NEVER bypass it and directly perform restore, rollback, or recovery**.
   - If a background execution path cannot reach the coordinator, it must either spawn an isolated coordinator that successfully acquires `spendx_restore.lock`, or **safely abort** with `RestoreCoordinationException`.

## 8. Qualified Pure-Dart Collision Handling

- In standard Dart `dart:io`, `File.rename()` wraps POSIX `rename(2)`, which silently and atomically overwrites an existing destination file. Dart provides no standard API for `RENAME_NOREPLACE`.
- **Pure Dart Vacancy Check Behavior:**
  - Before invoking `File.rename()`, the engine performs an explicit vacancy check:
    ```dart
    if (File(destinationPath).existsSync()) {
      throw DestinationCollisionException(
        'Destination $destinationPath unexpectedly exists. Aborting rename to prevent overwrite.'
      );
    }
    ```
  - If a destination is detected during this check, the engine executes an immediate **safe abort**, preserving both source and destination without modification.
- **Explicit TOCTOU Race Qualification:**
  - However, if an external uncoordinated process creates `destinationPath` *between* `existsSync()` and `File.rename()`, POSIX `rename(2)` will overwrite it.
  - Therefore, the pure Dart fallback **must never be described as atomic no-replace or as protection against non-cooperating external writers**.
  - It is documented as an **unresolved OS primitive limitation** when running in pure Dart without native FFI extensions.

## 9. File Lock Lifecycle & Platform Semantics Analysis

### 9.1 In-Process Limitation of Dart `RandomAccessFile.lock()`
- **Dart VM Runtime Primitive:** In the Dart SDK C++ source (`runtime/bin/file_posix.cc`), `RandomAccessFile.lock()` calls standard POSIX **`fcntl(fd, F_SETLK, &fl)`**.
- **Process-Associated Semantics:** POSIX `fcntl` record locks are owned by the **OS Process (`struct proc` / PID)**, not by individual threads, isolates, or open file descriptors.
- **The In-Process Failure:** The official Dart API documentation explicitly states:
  > *"On Linux and OS X, lock() is implemented using `fcntl`. Therefore, the lock is associated with the process, not the file descriptor. If two isolates within the same process try to lock the same file, the second lock() will succeed, even if FileLock.exclusive is used."*
- **Consequence for SpendX Concurrency:**
  1. **Multiple Isolates in Same Engine:** Dart isolates in the same process do not block each other; both obtain "exclusive" locks simultaneously.
  2. **Separate Flutter Engines in Same Process:** In Android, background execution callbacks (such as `notificationTapBackground` in [`notification_service_v2.dart`](file:///Users/sivek/Documents/SpendX/lib/services/notification_service_v2.dart#L1366)) run in a separate `FlutterEngine` hosted inside the **same OS process**. If both the foreground UI engine and the background engine call `RandomAccessFile.lock()` on `spendx_restore.lock`, **both succeed concurrently**.
  3. **Conclusion:** Dart's `RandomAccessFile.lock()` **cannot independently protect multiple isolates or separate Flutter engines within the same OS process**.

### 9.2 Linux Incompatibility: `fcntl` Record Locks vs Native `flock`
- **Independent Kernel Lock Subsystems:** On Linux (including Android Linux kernel `fs/locks.c`), `fcntl()` record locks and `flock()` open file table locks operate in completely separate, non-interacting subsystems:
  - `flock()` places `FL_FLOCK` locks associated with the `struct file` (open file description).
  - `fcntl()` places `FL_POSIX` locks associated with `struct files_struct` (process table / PID).
- **Zero Conflict Interoperability:** The Linux VFS kernel does **not** check `FL_POSIX` against `FL_FLOCK`. A process holding an exclusive `flock(fd, LOCK_EX)` on `spendx_restore.lock` will **NOT** block another process holding `fcntl(fd, F_SETLK, F_WRLCK)` on the exact same lockfile!
- **Mandate:** Claiming that using the same lockfile path makes different locking primitives interoperable is fundamentally false. All cooperating participants accessing the database or executing recovery must use a strictly compatible, verified locking protocol.

### 9.3 Process Lock Lease Manager (Tier 1) & Descriptor Ownership Model

#### 1. Execution Context Inventory & Mandatory Quiescence Verification
**Prohibition Against False Proof of Quiescence:**  
None of the following signals, independently or in combination, constitutes proof that database access has ceased:
- Heartbeat timeout.
- Coordinator isolate exit event.
- Forceful termination via `Isolate.kill()`.
- `FlutterEngine` destruction notification.
- Cancellation token completion.

Force-killing a Dart isolate terminates only user-space Dart bytecode execution; it does **not** stop native background threads, in-flight SQLite C library calls, or plugin worker queues already dispatched by the host process.

##### Authoritative Inventory of Database-Capable Execution Contexts:
| Context # | Execution Context | Concrete Mechanism | Stopping Procedure | Confirmation Criterion |
| :--- | :--- | :--- | :--- | :--- |
| **EC-01** | **Coordinator Isolate** | Dedicated Dart isolate executing restore flow | Cancellation signal sent via port; if unresponsive, `Isolate.kill(priority: immediate)` | `Isolate.addOnExitListener` fires and delivers termination event to listener port |
| **EC-02** | **Root & Auxiliary Dart Isolates** | UI isolate or `compute()` worker isolates accessing database | Gated by application-level restore coordination flag (`isDatabaseLockedForRestore = true`) | Synchronous ACK received from root database provider confirming zero active transactions |
| **EC-03** | **Plugin-Managed Worker Threads** | `sqflite` native Android `HandlerThread` / `ExecutorService` | Dispatch queue cancellation via `closeDatabase()` or drain task submission | Submission of barrier task to plugin executor completes (`executor.submit(() -> {}).get()`) |
| **EC-04** | **Native SQLite / SQLCipher Engine** | In-flight C library execution, WAL auto-checkpoint, pager threads | Await return of active C function; issue `sqlite3_interrupt()`; close connection via `sqlite3_close_v2()` | `sqlite3_close_v2()` returns `SQLITE_OK`, or `sqlite3_next_stmt(db, null) == null` confirming zero open statements |
| **EC-05** | **Asynchronous I/O Workers** | Platform channel streaming workers, file copy buffers, stream decoders | Stream cancellation and buffer cancellation signaled | All pending I/O `Future` completions observed; underlying file descriptors closed |

##### The Mandatory Quiescence Invariant:
If **ANY** of the five execution contexts cannot be confirmed stopped:
- The manager **MUST RETAIN THE PROCESS LEASE AND OS FILE LOCK**.
- The manager **MUST NOT** permit another restore, rollback, or database operation.
- The state transitions to **`CoordinatorState.indeterminate`**. All subsequent callers receive `RestoreIndeterminateException`.

#### 2. Differentiated Lock Release & Cleanup Failure State Machine
Release is not an unconditional reset. SpendX implements a strict 4-way outcome state machine:

```text
                                  +-----------------------+
                                  | release(leaseToken)   |
                                  +-----------------------+
                                              |
                             Validate leaseToken == activeLease.token
                                              |
                       +----------------------+----------------------+
                       | Valid                                      | Mismatch (Stale)
                       v                                            v
         Attempt FileLock.release()                      [Outcome D: STALE_REJECTED]
                       |                                 - Active lease untouched
            +----------+----------+                      - Descriptor untouched
            | Success             | Throws / Uncertain   - Zero state change
            v                     v
   Attempt channel.close()   [Outcome B: INDETERMINATE]
            |                - Retain lock & lease
     +------+------+         - Reject new acquisitions
     |             |         - Requires process restart / retry
     | Success     | Throws
     v             v
[Outcome A:    [Outcome C: DESCRIPTOR_CLEANUP_FAILED]
 UNLOCKED]     - FileLock was released at OS level
 - Lease clear - File descriptor leaked / unclosed
 - Ready       - Reject new acquisitions to prevent POSIX hazards
               - Do NOT claim cleanup succeeded
```

##### Outcome Specifications:
- **Outcome A: Full Success (`State: UNLOCKED`):**
  - `FileLock.release()` returns successfully without error.
  - `FileChannel.close()` returns successfully without error.
  - Action: `activeLease` is set to `null`; manager state transitions to `UNLOCKED`.
- **Outcome B: Release Failure or Uncertainty (`State: INDETERMINATE`):**
  - `FileLock.release()` throws `IOException` or execution times out.
  - Action: The manager does **not** assume the OS lock was released. The lease is **retained**. Manager state transitions to `INDETERMINATE`. All subsequent acquisition requests are strictly rejected with `RestoreIndeterminateException`.
- **Outcome C: Descriptor Close Failure (`State: DESCRIPTOR_CLEANUP_FAILED`):**
  - `FileLock.release()` succeeded, but `FileChannel.close()` throws `IOException`.
  - Action: The manager records a descriptor leak. Because closing descriptors later could trigger POSIX `fcntl` silent release bugs on active locks, the manager transitions to `DESCRIPTOR_CLEANUP_FAILED`. It does **not** claim cleanup succeeded and rejects new acquisitions until the host process restarts.
- **Outcome D: Token Mismatch (`State: STALE_REJECTED`):**
  - Caller supplies a `leaseToken` that does not match `activeLease.token`.
  - Action: The manager performs **zero modifications** to the active lease or descriptor. Returns `STALE_LEASE_TOKEN`.
- **Acquisition Rollback Parity:** If `tryLock()` returns `null` or throws, and the subsequent cleanup `channel.close()` throws `IOException`, the manager transitions to `DESCRIPTOR_CLEANUP_FAILED` rather than claiming the state is `UNLOCKED`.

#### 3. Acquisition-in-Progress Lifecycle & Mid-Transition Interruption
The manager explicitly governs engine destruction or cancellation during every acquisition transition:

| Transition Point | State Name | Descriptor Status | OS Lock Status | Authoritative Owner | Cleanup Protocol on Engine Destruction / Cancel |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Transition 1** | `LEASE_ACQUIRING_PRE_OPEN` | Not yet opened | None | Manager | Revert state to `UNLOCKED`. Zero descriptor to close. |
| **Transition 2** | `LEASE_ACQUIRING_FD_OPEN` | Opened (`channel != null`) | None (pre-tryLock) | Manager | Manager closes `channel`. If close throws `IOException`, transition to `DESCRIPTOR_CLEANUP_FAILED`. Otherwise `UNLOCKED`. |
| **Transition 3** | `LEASE_ACQUIRING_LOCK_HELD` | Opened (`channel != null`) | Held (`fileLock != null`) | Manager | Manager calls `fileLock.release()` and `channel.close()`. If release fails $\rightarrow$ `INDETERMINATE`. If close fails $\rightarrow$ `DESCRIPTOR_CLEANUP_FAILED`. If both succeed $\rightarrow$ `UNLOCKED`. |
| **Transition 4** | `LEASE_GRANTING` | Opened | Held | `activeLease` | Full release protocol (Section 9.3.2) executed. |

#### 4. Duplicate Acquisition Policy: Strict Single-Lease Non-Reentrant Rejection
SpendX strictly rejects re-entrant acquisitions:
- If an engine attempts to call `acquire()` while that engine already owns an active lease, the manager strictly **REJECTS** with `DUPLICATE_ACQUISITION_REJECTED`.
- Zero re-entrancy and zero reference counting. Eliminates all partial cancellation, over-release, and ABA permit hazards.

#### 5. Authoritative Lockfile Ownership Model
- **Sole Opener:** Android Host Process Lock Manager (`SpendXProcessLockLeaseManager`).
- **Sole Descriptor Owner:** Host Manager owns the single `FileChannel` instance.
- **Dart Isolation:** Dart code never opens `spendx_restore.lock`; holds only opaque `leaseToken`.
- **Cross-Process:** Distinct PIDs participate via `fcntl(F_SETLK)`. Isolated kernel file tables prevent external descriptor close events from affecting the SpendX host lock.

### 9.4 Platform Scope Resolution: Exclusion of iOS in 2.1.0
- **Android Target:** Fully supported and specified (Tier 1 JVM `SpendXProcessLockLeaseManager` + Tier 2 POSIX `fcntl` on `spendx_restore.lock`).
- **iOS Target:** **EXCLUDED from SpendX 2.1.0 release scope.** Formally marked as **`Limitation LIM-PLAT-01-IOS: iOS Portable Restore Excluded`**:
  - *Rationale:* No physical iOS hardware is attached to the CI/CD test harness; iOS runtimes do not execute a JVM (making Android JVM lease management inapplicable); native Darwin process synchronization (`os_unfair_lock` / serial dispatch queues) is not implemented in this milestone.
  - *Boundary Rule:* Pure Dart cannot guarantee atomic cross-engine or cross-process safety on iOS without native code extensions.
  - *Integrity Policy:* No proposed iOS mechanism is described as implemented or verified. iOS portability is formally deferred to a post-2.1.0 milestone.

### 9.6 Corrected Database Access Gate Protocol (DAG-01) & Pillar 4.5A.2 Requirements

Because existing repositories access `AppDatabase.instance.database` directly without admission control, true database quiescence **cannot be enforced by documentation or by Dart-only flags alone**. 

SpendX defines the **Corrected Database Access Gate (DAG-01)** protocol. Under this protocol, dual-tier restore ownership (Tier 1 process lease and Tier 2 OS POSIX file lock) **must be acquired FIRST**, before any destructive preparation, admission closure, or connection teardown:

```text
[Initiate Restore / Rollback / Recovery]
                   │
                   ▼
┌────────────────────────────────────────────────────────┐
│ Phase 1: Establish Dual-Tier Restore Ownership         │
│  - Tier 1: Acquire JVM Process Lease                   │
│  - Tier 2: Acquire Exclusive POSIX fcntl File Lock     │
└────────────────────────────────────────────────────────┘
                   │ (If acquisition fails -> Abort immediately; zero state change)
                   ▼
┌────────────────────────────────────────────────────────┐
│ Phase 2: Atomic Admission Closure                      │
│  - Step 2a: Native Admission Closure (closeNative())   │ ──► Rejects new native background tickets
│  - Step 2b: Dart Admission Closure (closeDart())       │ ──► Rejects new foreground queries
└────────────────────────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────────────────────┐
│ Phase 3: Active Operation Drainage (Timeout: 5000 ms)  │
│  - Await activeDartOperations == 0                     │
│  - Await activeNativeTickets == 0                      │
└────────────────────────────────────────────────────────┘
                   │
        ┌──────────┴──────────┐
        │ Drain Timeout       │ Drain Succeeded (Both == 0)
        ▼                     ▼
┌─────────────────┐   ┌────────────────────────────────────────────────────────┐
│ Coordinated     │   │ Phase 4: Explicit Connection Teardown                  │
│ Timeout         │   │  - AppDatabase.instance.close()                        │
│ Rollback        │   └────────────────────────────────────────────────────────┘
│                 │                            │
└─────────────────┘                            ▼
                      ┌────────────────────────────────────────────────────────┐
                      │ Phase 5: Plugin Worker Queue Drain                     │
                      │  - Dispatch barrier task to HandlerThread looper       │
                      │  - Confirm executor queue is idle                      │
                      └────────────────────────────────────────────────────────┘
                                               │
                                               ▼
                      ┌────────────────────────────────────────────────────────┐
                      │ Phase 6: Restore Journal Preparation                   │
                      │  - Write spendx_restore_journal.json (state: swapping) │
                      │  - fsync(file_fd) and fsync(dir_fd)                    │
                      └────────────────────────────────────────────────────────┘
                                               │
                                               ▼
                      ┌────────────────────────────────────────────────────────┐
                      │ Phase 7: Atomic Database Replacement (6-Step Protocol) │
                      │  - Move active to quarantine (no-replace)              │

                      │  - Release Tier 2 OS lock and Tier 1 lease             │
                      └────────────────────────────────────────────────────────┘
```

#### Required Production Architecture Changes (Pillar 4.5A.2)
To implement DAG-01 safely in production code during Pillar 4.5A.2:
1. **Centralized Database Gateway:** Modify `AppDatabase.database` to return `GatedDatabase` which intercepts every query/mutation and tracks active operations via atomic tickets.
2. **Operation-Scoped Native Tickets:** Implement `acquireDatabaseOperationTicket(engineId)` and `releaseDatabaseOperationTicket(ticketId)` in `SpendXProcessLockLeaseManager` to eliminate TOCTOU flaws in auxiliary engines (`notificationTapBackground`).
3. **Writer Participation in OS Lock Protocol:** All normal database writers acquire a shared read lock on `spendx_restore.lock`, ensuring they serialize with the coordinator's exclusive restore lock.
4. **Elimination of Unawaited Calls:** Refactor `notification_service_v2.dart` and `live_sms_service.dart` to route background tasks through `TrackedDatabaseTaskQueue`.
5. **Coordinated Timeout Rollback:** If drain times out after 5000 ms, restore aborts, files remain untouched, both gates reopen symmetrically, and the OS lock is released.

### 9.7 SQLite Quiescence Semantics: Connection-Level vs Database-Wide

To prevent false assertions regarding SQLite behavior, SpendX formally documents the exact C-level SQLite semantics:

| C API / SQL Command | Operational Scope | Actual SQLite Semantics | Quiescence / Safety Implication |
| :--- | :--- | :--- | :--- |
| `sqlite3_close_v2()` | **Single Connection (`sqlite3*`)** | If prepared statements, blobs, or backup operations remain unfinalized, `sqlite3_close_v2()` returns `SQLITE_OK`, but **marks the connection as a zombie**. The OS file descriptor and OS file locks remain open until statements finalize! | Calling `close_v2()` does **not** guarantee file locks are released. Statements must be explicitly finalized. |
| `sqlite3_next_stmt()` | **Single Connection (`sqlite3*`)** | Iterates over prepared statements associated strictly with **one specific database connection handle**. Returns `NULL` when all statements on that handle are finalized. | **FFI-Only Primitive:** Accessible only on direct `package:sqlite3` C handles. It is **not accessible on `sqflite.Database` handles over platform channels** and cannot be used as an acceptance criterion for `sqflite`. |
| `sqlite3_interrupt()` | **Single Connection (`sqlite3*`)** | Sets an interrupt flag strictly on **one specific database connection handle**. Aborts queries currently evaluating on that handle. | Does **not** abort transactions on other connections. Does **not** prevent subsequent queries from being queued. |
| `PRAGMA wal_checkpoint(TRUNCATE)` | **Database-Wide File Coordination** | Checkpoints all WAL frames into the database file and truncates the WAL file to zero bytes. Requires exclusive write access to WAL. | If **any other connection** holds an uncommitted read transaction, `TRUNCATE` fails or blocks with `SQLITE_BUSY`. Must close all readers first. |

**Architectural Rule:** Connection-level primitives (`close_v2`, `next_stmt`, `interrupt`) must never be asserted as providing database-wide quiescence. Database-wide quiescence requires closing **all** open connections across all engines, draining native plugin queues, and isolating the database file via Tier 2 OS process locks.

### 9.8 Process-Local vs OS-Level Lock Failure Matrix

When `FileLock.release()` or `FileChannel.close()` throws an exception, the host runtime is in a state of OS-level lock uncertainty. SpendX specifies an authoritative 4-outcome failure matrix:

| Failure Scenario | Process-Local Lease State | OS-Level Lock State | External Process Acquisition | Kernel FD Table Status | Required Recovery Action |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1. `FileLock.release()` throws `IOException`** | Retained (`INDETERMINATE`) | **UNCERTAIN** (Kernel may or may not have cleared lock) | **UNCERTAIN** (External process may block or acquire) | Descriptor remains open in kernel table | **Process Termination REQUIRED**. Dart/JVM cannot verify OS release. OS kernel process termination is the only definitive mechanism to guarantee lock reclamation. |
| **2. `FileChannel.close()` throws `IOException` after successful release** | Retained (`DESCRIPTOR_CLEANUP_FAILED`) | **CONFIRMED RELEASED** (Kernel cleared lock during `release()`) | **CAN ACQUIRE** (External process can obtain lock) | Leaked descriptor in kernel table | **Process Termination REQUIRED**. Prevents future `fcntl` silent unlock bugs on reused file descriptors. |
| **3. Rollback `channel.close()` throws `IOException` after null `tryLock()`** | Retained (`DESCRIPTOR_CLEANUP_FAILED`) | **CONFIRMED HELD BY EXTERNAL PROCESS** | **HELD BY EXTERNAL** | Leaked descriptor in kernel table | **Process Termination REQUIRED**. External owner remains authoritative; SpendX cleans host process state. |
| **4. Clean Release (`release()` & `close()` succeed)** | `UNLOCKED` | **CONFIRMED RELEASED** | **CAN ACQUIRE** | Descriptor closed and removed | None. Safe for subsequent acquisitions. |

**Inviolable Principle of Lock Uncertainty:** Dart VM and Android ART JVM runtimes cannot guarantee OS-level lock release if the release syscall throws. When a release call fails, the lock status is classified as **Uncertain**, the lease is retained as **Indeterminate**, and full process restart is required.

### 9.9 Five-Stage Completion and Durability Separation

To avoid conflating execution milestones with physical durability guarantees, SpendX establishes five distinct, non-fungible stages:

```text
┌────────────────────────────────────────────────────────┐
│ Stage 1: Operation Quiescence                          │ ──► Zero threads/workers executing database queries
└────────────────────────────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ Stage 2: Transaction Completion                        │ ──► SQLite returns SQLITE_OK on COMMIT / ROLLBACK
└────────────────────────────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ Stage 3: Integrity Validation                          │ ──► 7-stage validation passes (Header, PRAGMA, FK, Accounting)
└────────────────────────────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ Stage 4: File Data Durability                          │ ──► POSIX fsync(file_fd) returns 0 without error
└────────────────────────────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ Stage 5: Directory Metadata Durability                 │ ──► POSIX fsync(dir_fd) returns 0 without error
└────────────────────────────────────────────────────────┘
```

1. **Stage 1 (Operation Quiescence):** Confirms that all application repositories, Dart isolates, background `FlutterEngines`, and native `sqflite` worker threads have completed and stopped querying the database.
2. **Stage 2 (Transaction Completion):** Confirms that SQLite's internal storage engine has completed a transaction and returned `SQLITE_OK`. Pages may still reside strictly in OS page cache memory buffers.
3. **Stage 3 (Integrity Validation):** Confirms that the database pages on disk or in cache pass all 7 integrity and accounting invariant checks.
4. **Stage 4 (File Data Durability):** Confirms that POSIX `fsync(file_fd)` has executed without error, flushing dirty file data blocks from volatile kernel page cache to physical storage.
5. **Stage 5 (Directory Metadata Durability):** Confirms that POSIX `fsync(dir_fd)` has executed without error on the parent directory, ensuring that atomic directory entries (e.g. renames of `spendx.db.restored` to `spendx.db`) persist across sudden power loss.

## 12. Independent Risk Assessment

An independent architectural risk evaluation was conducted across the portable-backup subsystem:

1. **Physical Hardware Lock Contention (High Residual Risk — Gated):**
   - *Risk:* Dart VM POSIX `fcntl` semantics and Android ART JVM `FileChannel.lock()` interactions have not been validated on physical Android hardware due to build harness sandbox constraints.
   - *Mitigation:* Formally gated under `Gate G-SEC-01-LOCK`. Production merge is strictly blocked until physical device tests L-01 through L-27 pass.
2. **Current Repository Coordinator Bypass (High Residual Risk — Implementation Pending):**
   - *Risk:* 15 repositories currently bypass `DatabaseLifecycleCoordinator` and call `AppDatabase.instance.database` directly.
   - *Mitigation:* DAG-01 protocol specifies required production changes for Pillar 4.5A.2: centralized admission gateway, elimination of unawaited futures, and cross-engine IPC barriers.
3. **Crash During Unsynchronized Directory Fallback (Medium Residual Risk):**
   - *Risk:* In pure Dart runtimes where native directory `fsync` is unavailable, sudden power loss during rename may leave directory metadata uncommitted.
   - *Mitigation:* Durability status is explicitly recorded as `Durability Unconfirmed`; safety backups and journal are retained with `state: cleanupPending`.
4. **Low-Memory Device KDF Exhaustion (Low Residual Risk):**
   - *Risk:* Argon2id parameter negotiation (64 MiB RAM) could trigger Android OS LMK (Low Memory Killer) on budget devices (1 GB RAM).
   - *Mitigation:* Hard bounds (8..128 chars, max 64 MiB, max 10 iterations) enforced before KDF invocation; memory allocation monitored.
5. **iOS Platform Exclusion (Managed Release Limitation):**
   - *Risk:* Cross-platform expectations from iOS users.
   - *Mitigation:* Formally documented under `Limitation LIM-PLAT-01-IOS`; clear user-facing error messaging prevents silent corruption.
