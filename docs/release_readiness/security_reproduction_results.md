## 2. SEC-01 — Cross-Device SQLCipher Backup Restoration Deadlock

### 2.1 Root Cause
In [`lib/services/backup_service.dart`](file:///Users/sivek/Documents/SpendX/lib/services/backup_service.dart#L207), database snapshotting is performed using SQLite native `VACUUM INTO`:
```dart
await db.execute("VACUUM INTO '${snapFile.path}';");
```
When `db` is an encrypted SQLCipher connection, `VACUUM INTO` creates a snapshot file that inherits the cryptographic key of the source database (`PRAGMA key = "x'...'"` from Device A).

[`BackupFileService.createPackage`](file:///Users/sivek/Documents/SpendX/lib/services/backup_file_service.dart#L63-L132) wraps this snapshot in an outer layer of AES-256-GCM encryption derived from the user's backup password via Argon2id. However, the inner SQLCipher database key remains Device A's unique 256-bit hardware key generated by `SpendXDatabaseKeyManager`.

When the user restores on Device B (or a fresh installation after application reinstall):
1. Outer decryption with the user's password succeeds, yielding `staged.stagedDbFile`.
2. [`BackupService.restoreFromFile`](file:///Users/sivek/Documents/SpendX/lib/services/backup_service.dart#L451-L460) checks `DatabaseEncryptionMigrationService.isPlaintextSqliteFile(staged.stagedDbFile.path)`. Because the file is encrypted with Device A's key, it is not plaintext SQLite.
3. The restore path invokes:
   ```dart
   final key = await SpendXDatabaseKeyManager.instance.getOrCreateKey();
   final blobKey = SpendXDatabaseKeyManager.keyToSqlCipherBlob(key);
   stagedDb = await SpendXDatabaseFactory.instance.openEncryptedDatabase(
     staged.stagedDbFile.path,
     password: blobKey,
   );
   ```
4. Device B queries its own `FlutterSecureStorage` (Key B). SQLCipher attempts to authenticate the header with Key B and fails immediately with `SqlCipherException: SQLITE_NOTADB or corrupted header`.
5. Device B is permanently locked out of restoring the backup archive.

### 2.2 Exact Source Files & Line Ranges
- [`lib/services/backup_service.dart`](file:///Users/sivek/Documents/SpendX/lib/services/backup_service.dart#L198-L225): `VACUUM INTO` execution without key re-encryption or detachment.
- [`lib/services/backup_service.dart`](file:///Users/sivek/Documents/SpendX/lib/services/backup_service.dart#L441-L469): Restoration assumes local device key matches inner database key.
- [`lib/services/backup_file_service.dart`](file:///Users/sivek/Documents/SpendX/lib/services/backup_file_service.dart#L60-L133): Treats `snapFile` as opaque bytes without resolving nested SQLCipher encryption.

### 2.6 Severity & Verdict
- **Severity:** **CRITICAL** (Loss of user financial records when migrating devices or reinstalling app).
- **Verdict:** **CONFIRMED**

### 2.7 Recommended Remediation Options (Recommendations Only)
- **Option 1 (Password-Only Archive Encryption):** In `BackupService.createBackupPackage()`, export the snapshot to a temporary unencrypted SQLite database (`ATTACH DATABASE ... AS staging KEY ''; SELECT sqlcipher_export('staging');`), and then encrypt that file exclusively via AES-256-GCM using the user's backup password. Upon restore, decrypt with the password, validate integrity, and re-encrypt the database with the local device's SQLCipher key.
- **Option 2 (Archive Key Rekeying):** Use `PRAGMA rekey` or `sqlcipher_export` to re-key the inner database to a key derived from the backup password, ensuring outer and inner keys are synchronized.

## 3. SEC-02 — Gemini Credential Architecture & Client Exposure

### 3.1 Root Cause
SpendX implements AI features (chat assistant, receipt scanning, statement OCR) via [`lib/services/gemini_service.dart`](file:///Users/sivek/Documents/SpendX/lib/services/gemini_service.dart). The key retrieval logic provides only two configuration paths:
1. `dotenv.env['GEMINI_API_KEY']` loaded from `.env` on line 17.
2. `String.fromEnvironment('GEMINI_API_KEY', defaultValue: '')` on line 21.

There is zero user-facing settings UI for users to supply their own Gemini API key (BYOK). The architecture assumes the key is developer/application-owned.

### 3.2 Key Ownership & Embedding Analysis
- **Key Ownership:** **100% Application-Owned (Developer-Provided).** No user input screen exists in Settings or onboarding.
- **Release Artifact Inspection:**
  - File: `build/app/outputs/flutter-apk/app-release.apk`
  - Build Timestamp: `Oct 7, 2026, 13:06`
  - SHA-256: `42104dcb2febfa329623d51a7775787372c869a38c8b30a690e9ea4186c22406`
  - SHA-1: `ebd3a0c5aaf06cd33c24c212d2e39e7c0426a2fb`
  - Probing packaged assets: `unzip -l app-release.apk | grep -i "\.env"` returned zero hits (`.env` was not bundled).
  - Probing compiled Dart AOT text sections: `unzip -p app-release.apk lib/arm64-v8a/libapp.so | strings | grep -i "AIzaSy"` returned zero hits.
- **Exposure in Current Build:** The current Oct 7 release APK does NOT contain the key.
- **Consequence in Current Build:** Because the key was omitted, all AI capabilities in the release build fail immediately with:
  - Chat: `"Error: Gemini API key is not configured. AI features require an API key."`
  - Receipt scan: `{'error': 'Gemini API key is not configured.'}`
  - Statement scan: `[{'error': 'Gemini API key is not configured.'}]`
- **Architectural Dilemma:** If the developer provides the key for production releases via `--dart-define=GEMINI_API_KEY=<REDACTED>`, the key is compiled directly into the Dart AOT binary (`libapp.so`). Because Google AI Studio Gemini API keys cannot be restricted by Android application signing fingerprint (unlike Google Maps SDK keys), any user extracting `libapp.so` can make arbitrary requests against the developer's quota.

### 3.3 Exact Source Files & Line Ranges
- [`lib/services/gemini_service.dart`](file:///Users/sivek/Documents/SpendX/lib/services/gemini_service.dart#L14-L24): Key retrieval mechanism.
- [`lib/main.dart`](file:///Users/sivek/Documents/SpendX/lib/main.dart#L39-L43): `.env` loading silently catches exceptions in release builds.
- [`android/app/build/intermediates/assets/release/mergeReleaseAssets/flutter_assets/.env`](file:///Users/sivek/Documents/SpendX/android/app/build/intermediates/assets/release/mergeReleaseAssets/flutter_assets/.env): Proves older release build intermediate bundled plaintext `.env` containing OAuth and Gemini secrets.

### 3.4 Severity & Verdict
- **Severity:** **HIGH** (Architectural exposure of developer credentials if bundled; total feature failure if omitted).
- **Verdict:** **CONFIRMED**

### 3.5 Recommended Remediation Options (Recommendations Only)
- **Option 1 (User-Provided Key - BYOK):** Add a "Gemini API Key" field under Settings -> AI Features, storing the user's personal key securely in `FlutterSecureStorage`.
- **Option 2 (Backend Proxy):** Deploy a lightweight backend service (e.g. Firebase Cloud Function / Cloud Run) that verifies Firebase App Check / user authentication tokens before forwarding queries to Gemini, keeping master credentials off mobile devices.

## 4. SEC-03 — Plaintext Migration Rollback on Cleanup Failure

### 4.1 Root Cause
In [`lib/data/security/database_encryption_migration_service.dart`](file:///Users/sivek/Documents/SpendX/lib/data/security/database_encryption_migration_service.dart#L907-L953):
```dart
await journal.record(MigrationState.verified);

// Cleanup archives and temporary files
if (await archiveFile.exists()) {
  await archiveFile.delete();
}
if (!keepBackupOnSuccess) {
  final bkp = File(rollbackBackupPath);
  if (await bkp.exists()) await bkp.delete();
}
```
At this point in the state machine:
- The live database has already been swapped and verified as SQLCipher.
- `archiveFile` (`spendx.db.pre_encrypted_archive`) has been deleted.
- If `bkp.delete()` throws any filesystem exception (e.g. permission restriction, filesystem lock, or I/O error), execution jumps into `catch (e, stack)` on line 933.
- The catch block checks:
  ```dart
  if (journal.state == MigrationState.swapping ||
      journal.state == MigrationState.verified) {
    await journal.record(MigrationState.recoveryRequired, err: e.toString());
    await _rollbackSwap(
      sourcePath: sourcePath,
      archivePath: archivePath,
      rollbackBackupPath: rollbackBackupPath,
    );
  }
  ```
- In `_rollbackSwap()`:
  ```dart
  if (await archiveFile.exists()) {
    if (await liveFile.exists()) await liveFile.delete();
    archiveFile.renameSync(sourcePath);
  } else if (await bkpFile.exists()) {
    if (await liveFile.exists()) await liveFile.delete();
    await bkpFile.copy(sourcePath);
  }
  ```
- Because `archiveFile` was already deleted, `bkpFile.exists()` matches.
- `_rollbackSwap` **deletes the live encrypted database** and **copies the plaintext pre-migration backup over `sourcePath`**!
- The live database reverts to unencrypted plaintext storage.

### 4.2 Exact Source Files & Line Ranges
- [`lib/data/security/database_encryption_migration_service.dart`](file:///Users/sivek/Documents/SpendX/lib/data/security/database_encryption_migration_service.dart#L909-L916): Unhandled cleanup deletion.
- [`lib/data/security/database_encryption_migration_service.dart`](file:///Users/sivek/Documents/SpendX/lib/data/security/database_encryption_migration_service.dart#L936-L953): Catch block treating post-verification cleanup failure as an emergency rollback trigger.
- [`lib/data/security/database_encryption_migration_service.dart`](file:///Users/sivek/Documents/SpendX/lib/data/security/database_encryption_migration_service.dart#L971-L989): `_rollbackSwap` unconditionally replacing live DB with plaintext backup.

### 4.3 Reproduction Procedure
1. Created test `SEC-03-A` in [`test/features/security_findings_reproduction_test.dart`](file:///Users/sivek/Documents/SpendX/test/features/security_findings_reproduction_test.dart#L273-L395):
   - Created a plaintext Schema v24 database with accounts and data.
   - Executed `runMigration` to successful swap and verification.
   - Simulated cleanup failure where `spendx.db.pre_migration_backup` cannot be unlinked.
   - Evaluated state machine recovery behavior when journal enters `recoveryRequired`.
   - Verified active database encryption status before and after rollback.

### 4.4 Expected vs Actual Result
- **Expected:** Once a database has been verified as SQLCipher at Checkpoint 8, a failure to delete a leftover backup file should log a warning and leave the active encrypted database running.
- **Actual Result:**
  - Active encrypted database was deleted.
  - Plaintext pre-migration backup was copied over the live database path.
  - Active database header was tested with `isPlaintextSqliteFile()`: returned `true`.
  - The application silently reverted to unencrypted storage.

### 4.5 Severity & Verdict
- **Severity:** **MEDIUM** (Operational risk of silent rollback from encrypted to plaintext storage).
- **Verdict:** **CONFIRMED**

### 4.6 Recommended Remediation Options (Recommendations Only)
- In `DatabaseEncryptionMigrationService.dart`, wrap lines 909–916 in a dedicated `try/catch` block that catches and logs any cleanup exceptions without propagating them to `_rollbackSwap`. Once Checkpoint 8 (`verified`) is logged, rollback must be strictly prohibited.
